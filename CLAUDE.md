# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A self-hosted Hanabi card game for a small group of friends (2–5 players). One player runs the server on their laptop; the others connect over a Tailscale tailnet by opening `http://<host>:3000` in a browser. No hosted service, no third-party signaling, no accounts.

## Commands

- `npm install` — first-time setup
- `npm start` — run the host (serves the client and accepts WebSocket connections on port 3000, override with `PORT=…`)
- `npm test` — run the pure-logic test suite (uses Node's built-in `node:test`)
- `node --test server/game.test.js` — run a single test file
- `PORT=3999 node server/index.js & sleep 0.6 && PORT=3999 node smoke.mjs` — end-to-end smoke test against a live WS server (`smoke.mjs` is the script)
- `npm run benchmark` (or `node benchmark.mjs --seeds N --players 2,3 --variants simple --end lax`) — deterministic bot-vs-bot score statistics over fixed seeds. Run it before and after any bot-brain change and put the numbers in the commit message; results are never committed as files since the same code always reproduces them.
- `npm run bot-scores` — compute the bot par score of every saved game that lacks one or whose stored par came from an older `BOT_VERSION` (see Bot par score). The server does the same pass in the background at boot; this is the one-off for a fresh library or right after a version bump.

Requires Node ≥ 20 (uses ES modules and `node:test`).

## Architecture

- **Host-authoritative**: the server holds the true game state and sends each client only what that player is allowed to see (your own hand identity is hidden from you, others' is visible). This is the only sane model for a hidden-information game like Hanabi — do not introduce client-side game state that could leak information by inspection.
- **Single repo, single process**: `server/` is Node + `ws`; `client/` is static HTML/JS served by the same Node process. No build step, no bundler.
- **Layered server modules**:
  - `variants.js` — variant definitions (pure data)
  - `game.js` — deck building, initial state, pile/score helpers (pure)
  - `rules.js` — action handlers (play/discard/hint/annotate), turn rotation, end conditions (pure mutations on state)
  - `stats.js` — per-player game statistics (pure): `gameStats(state, { botFlags })` counts plays / discards / hints given / hints received / undos and splits the clock per seat; `aggregateStats(games)` sums those per player *name* across games (except the time share, which is averaged per game — see Player stats)
  - `botScore.js` — bot par: replays a deck with a table of bots through the real rules engine and reports the score (pure; no filesystem, so `savedGame.js` can import it)
  - `view.js` — filters state into a per-viewer view (hides own card identities; gates the guarded-card flag on the share option; the note is owner-only and never shared)
  - `savedGame.js` — append-only JSONL game log under `saved-games/`, plus reconstruction (`loadSave`) used by the resume flow
  - `room.js` — a single game room: who's host, who's joined, action dispatch
  - `rooms.js` — in-memory registry of rooms (`Map<id, room>`) keyed by 6-hex ids, with `createRoom`/`getRoom`/`listRooms`/`addRoom`/`deleteRoom`/`summarizeRoom`. Rooms are ephemeral; only saved-game files persist across server restarts.
  - `index.js` — HTTP static server + WebSocket transport; routes each connection to at most one room at a time
  Keep game logic in `game.js` / `rules.js` and view filtering in `view.js`. The transport doesn't know game rules.
- **Per-card hint state**: every card carries `possibleColors`, `possibleNumbers`, `colorClued`, `numberClued`, `lastHints` (recent hint markers touching this card, see below), and `annotations` (a `{ note, guarded }` pair). Formal hints update the constraints; annotations are owner-controlled metadata. Cards in your own hand are sent to you WITHOUT their `color`/`number` fields, but WITH the inferred constraints — that's how you see "this could be red or rainbow" without seeing what it actually is. The `note` field is always private to the owner. The `guarded` boolean is visible to the owner; other players see it only when the lobby option `shareGuarded` is on.
- **Hint markers (`lastHints`)**: each hint gets a monotonic `hintIndex` from `state.nextHintIndex`. When a hint touches cards, `{ hintIndex, hintType, value }` is appended to each touched card's `lastHints` (newest last). A new hint never clears another hint's markers — multiple recent hints stack so the visualization can convey provenance. Two rules prune markers: (1) **consumption** — when a card leaves the hand (play OR discard, success or misplay), each of its `lastHints` entries is removed from every other card in the same hand (one card from the hint's touched set "using up" the hint clears the whole hint); (2) **cap** — at most `HINT_MARK_LIMIT=4` markers per card; when a touched card would exceed 4, its oldest hintIndex is dropped from every card in the hand. The client renders newest-at-center fanning to the right with overlap.
- **Saved games**: every started game opens a new `saved-games/<timestamp>-<variant>.jsonl` file. The first line is a `start` header (seed, variant, options, players, hostId, startedAt); each subsequent line is an event (`action`, `undo`, `rename`, `abandon-vote`, `end`). An `action` event may carry an optional `reasoning` string (≤200 chars): bots always record their decision reason, and the protocol accepts one from human clients too (no UI yet). Reconstruction stamps it on the action's log entry; live views strip it (it can reference hidden cards) — only the omniscient replay viewer (`viewerIndex -1`) and finished games show it. Writes use `fs.appendFile`, so a crash leaves at most one truncated trailing line which the loader tolerates. A natural game-end appends an `end` line but keeps the file open — if a player then undoes the game-ending move, the continuation is appended past the `end` and supersedes it on replay. Directory is gitignored; created at runtime. Two sidecars live beside the saves — `tags.json` and `bot-scores.json` (see Bot par score) — so everything derived or editable stays out of the replay data.
- **Deck import**: the lobby accepts a JSON file in the deck-order export format. The host's import is validated against the currently selected variant (exact multiset match + card-string format); a `bad_deck` error is returned otherwise. The pending deck shows in the lobby with a Clear button; it's re-validated at `startGame` time (in case the variant was changed) and then **cleared after the game starts** (one-shot). `createInitialState` takes an optional `deckCards` (draw order); save headers always include the post-shuffle/imported draw order under `deck`, with seed-shuffle as a fallback for older save files.
- **Resume on `npm start`**: on boot the server scans `saved-games/` for files whose last event isn't `end` (incomplete or continued past a previous end), and prompts the host in the terminal to pick one of the 3 most recent (or to type a filename). The prompt is skipped silently when stdin isn't a TTY or when `HANABI_NO_RESUME_PROMPT=1`. Resumed players come back marked `online:false`; their browsers reattach to the same seat via the existing `playerId`/name reconnect path. Tests can override the directory with `HANABI_SAVED_DIR`.

## Hint mechanics

Hint touch policy per suit:
- `self` — touched only by hints matching that suit's color (standard 5 colors)
- `all`  — touched by any color hint (rainbow)
- `none` — never touched by color hints (black)

Color hint logic in `applyColorHint`:
- Compute `touchedSet` = colors that would be touched by this hint (e.g. red hint in rainbow variant → `{red, rainbow}`).
- For each card: if it's touched, **intersect** `possibleColors` with `touchedSet`; otherwise **subtract** `touchedSet`.

This gives the receiving player both positive AND negative information automatically (e.g. after a red hint, untouched cards lose "red" and "rainbow" from their possible-colors set).

Hintable colors = suits with `hintMatches === 'self'`. Rainbow and black themselves are NOT hintable directly.

Hints that touch zero cards are rejected by default. The host can enable the `allowEmptyHints` lobby option to allow them as a negative-information signal (the hint still costs a token and rules out that color/number across the receiver's hand).

## Card display rules (client)

For each card the client computes:
- `faceColor` — for other players' cards: the actual color (already known to the viewer). For own cards: the color, if the owner's `possibleColors` has narrowed to a single non-black entry, OR to just `{black}`.
- `faceNumber` — same idea: the actual number for others, or the owner's `possibleNumbers` if narrowed to a single entry.

If neither is known, the card renders face-down. Black is treated as an *implicit* possibility: it's filtered out of the visible possible-color list, so a card narrowed to `{red, black}` is displayed as "red" on the face. The player accepts the convention that any narrowed result might silently also be black.

The partial-information row (small swatches and number badges under the card) is only rendered when the owner has *some* information but not full information, separately on each axis. A card with no color info AND no number info shows nothing under the face. A card with only color info shows only color swatches, and vice versa.

## End-of-deck rules

Configurable per game:
- `standard` — when the last card is drawn, each player gets exactly one more turn (set `finalTurn = turn + N + 1` at the moment of emptying).
- `lax` — keep playing until all hands are empty; empty-handed players are skipped.

Both modes also end on the third fuse (immediate loss) or perfect score.

## WebSocket protocol

Server → client: `hello` (variant list), `identity` (your assigned `playerId` plus the `roomId` and `roomName` you were placed in, and `isSpectator: true` if you joined as a spectator), `sync` (filtered view — either a `server-lobby` view or an `in-room` view), `error`, `roomCreated` (a resumed save landed in a fresh room; the client uses it to auto-enter), `deckExport`.

A fresh connection gets `hello` at once and its first `sync` (the server lobby) when the library listing is ready, which on a cold cache is not immediately. Incoming messages are **not** queued behind that greeting — a client that sends `createRoom`/`enterRoom` on connect is answered straight away, and the greeting is then dropped rather than sent, since it would stomp the in-room view the client just received. `send` marks a connection `synced` for that check, so the rule is simply "the greeting only lands on a connection nothing else has synced".

A view is one of:
- `kind: 'server-lobby'` — sent to connections that aren't in a room. Contains `rooms: [{ id, name, status, variantId, players, turn, allowSpectators, spectatorCount, ... }]`, `resumableSaves: [{ basename, variantId, playerNames, moves, ... }]`, and `library` — every save summarized (date, status, score/maxScore, players, tags; `seed` only when finished, since a live seed leaks the deck). Library summaries replay each file once and are cached by mtime (`listLibrary` in `savedGame.js`); **scans never overlap** — they are serialized through one promise chain, because a cold scan takes seconds (each save is replayed through the rules engine) and the cache only fills as each file finishes, so simultaneous scans would all miss and redo the same work (three at once measured 15.4s against 4.8s serialized). Each caller still gets its own scan rather than sharing the in-flight one, so a listing requested mid-scan reports each file as of its own turn. The cache is warmed on the background tick after `listen`, alongside the bot-par backfill, so the first player to open the lobby doesn't pay for it; the client renders them in a collapsed `<details>` "Game library" section with Review / Copy seed / Tags / Delete per row (Review is the label on the `replaySave` stepper — "Replay" read as "play this deck again", which is what branching and re-dealing a seed do), and each row's label is a button opening that game's info modal (`gameDetail`). Entries also carry `botScore` (the deck's bot par, finished games only — see Bot par score). Two fields of the cached entry never ship: `stats` and `deckKey` (`publicEntry` strips both). Per-player stats are computed alongside each library summary (same mtime cache) but **stripped from this view** — the lobby is re-broadcast after every action, so stats are fetched on demand via `statsSummary` instead.
- `kind: 'in-room'` — everything else you see today (lobby / playing / finished). Also carries `roomId` and `roomName` at the top level, plus `spectators: [{ id, name }]` (visible to everyone in the room) and `isSpectator: true` when the view belongs to a spectator connection. A spectator's view is built with `playerIndex` resolving to `-1` (the spectator id is never a seat), which is exactly the omniscient viewer index replay already uses — `viewCard` reveals every hand, own-hand annotations stay hidden (a spectator isn't the owner of anything), and `currentPlayer` never equals `-1` so every turn-gated control (Play/Discard/hint controls/tap-to-act/undo/abandon) renders as if it's simply nobody's turn. The client additionally hides the reaction bar for spectators.

Client → server:
- `createRoom { roomName?, playerName, playerId? }` — creates a fresh room and auto-joins the caller.
- `enterRoom { roomId, playerName, playerId? }` — joins an existing room as a player.
- `spectateRoom { roomId, playerName }` — joins as a spectator instead of a seat. Rejected with `spectators_disabled` unless the host has turned on the room's `allowSpectators` option (default off, lobby-only toggle, host-only). Allowed in either room phase — watching the pre-game lobby has no hidden information to protect. Spectator ids are never persisted client-side (no reconnect-by-id); a reload just re-sends `spectateRoom` for a fresh one. Spectators cannot take any seat-gated action — `play`/`discard`/`hint`/`undo`/`requestUndo`/`abandon`/`react`/`configure`/bot management/etc. all require a real seat and reject a spectator id the same way they'd reject an unknown one.
- `leaveRoom` — drop back to the server lobby (works for spectators too).
- `resumeSave { file, roomName? }` — spins up a new room from a saved game and returns `roomCreated`; the client then sends `enterRoom` for it. Refused with `save_in_use` when a room already holds that file (like delete/replay/branch): two rooms resumed from one save would both append to it, interleaving two divergent games into a log that can't be replayed apart.
- `replaySave { file, upto }` — stateless replay stepping: the server rebuilds the state after the first `upto` events of the save and replies `replayView { file, upto, total, view }`, where the view is omniscient (`viewerIndex: -1` reveals all hands). The view's `endedAt` is pinned to the timestamp of the last applied event (`loadSave`'s `lastAppliedAt`, falling back to `startedAt`), so the game timer shows the elapsed time of the original game up to that move instead of counting from the original start until now. Refused with `save_in_use` while a live room holds the file. The client shows it on the game screen with a step bar.
- `branchSave { file, upto, roomName? }` — "play from move N": copies the save's header plus its first `upto` events into a fresh `…-branch-….jsonl` save, resumes it into a new room (players offline, reclaimed by name), and replies `roomCreated`. The original save is untouched; the branch persists independently. Rejected (`bad_branch`) if the truncated game is already finished.
- `statsSummary { players?, variantId?, withPlayers?, from?, to?, tags?, untaggedOnly? }` — aggregate player stats over the saved games matching the filter (all filters optional; omitted means "all"). `withPlayers` is a list of names (≤8) that must **all** be in the game; combined with `players` it pins an exact table ("3-player games with Ann, Bob and Cid"). `from`/`to` are `YYYY-MM-DD` days (from `<input type="date">`), inclusive at both ends and read in the **host's local time** — malformed or empty means no bound. `tags` keeps games carrying **any** of the named tags (tags are categories; requiring all would mostly match nothing), and `untaggedOnly` keeps only games with no tags — the two are mutually exclusive, neither means "any tag". Replies `statsView { filter, available: { playerCounts, variantIds, playerNames, tags, firstDay, lastDay }, gamesMatched, gamesTotal, summary }`, where `summary` is `aggregateStats`'s output (one row per player name: games, plays, discards, hints, hintsReceived, undos, moves, moveMs, timeShareAvg). `available` is derived from the saves themselves, so the client's filter controls only offer game sizes, variants and names that exist (a selected name that no longer appears is dropped), and the date pickers are bounded by `firstDay`/`lastDay`, the span the library covers. `available.tags` is `[{ tag, count }]` ordered by how many games use each tag, capped at `STATS_TAG_LIMIT` (20). Rendered in the server lobby's collapsed "Player stats" section; requested when that section is opened and on every filter change.
- `gameDetail { file }` — everything the game-info modal shows for one save: the library row's fields, `stats` (the per-player table `gameStats` builds — the same one the game-over banner draws), `tags`, `botScore`, and `sameDeck`, the other saves dealt from the same deck (`{ basename, startedAt, variantId, status, score, maxScore, playerNames, playerBots, tags, botScore }` each, and each a link to its own info page in the client). Replies `gameDetailView { detail }`; `no_save` if the file is missing or unreadable. Asked for when a library row is clicked, so the per-game stats stay out of the lobby broadcast. **Deck identity is the draw order, not the seed** — the cached entry's `deckKey` is a hash of `initialDeckCards`, because one seed shuffles a *different* deck in a different variant, while an imported deck order reproduces the same deck under a fresh seed. `seed`, `botScore` and `sameDeck` are all withheld for a game that isn't finished, and `sameDeck` only ever relates finished games to each other: "this live game shares a deck with that finished one" hands over a deck you can read straight off the finished game's replay — the same reason `seed` is hidden while playing.
- `tagSave { file, tags }` — set a save's tags (≤8, ≤24 chars each), stored in the sidecar `saved-games/tags.json` so the JSONL format stays pure replay data. Tags show in the library list.
- `deleteSave { file }` — anyone may delete an incomplete save from the server lobby (saves carry no durable owner identity, and the tailnet is trusted). It's a soft delete: the file moves to `saved-games/trash/`, recoverable by the host from the terminal. Refused with `save_in_use` while an open room is appending to that file.
- `closeRoom` — host only; removes the room and kicks everyone back to the lobby.
- `deleteRoom { roomId, playerId }` — sent from the server lobby (where the connection holds no seat, so the client passes its persistent `playerId`). Allowed when the caller is the room's creator (`creatorId`, stamped at `createRoom`; falls back to the save's host for resumed rooms) or when the room is idle (no players, or every seat offline). Anyone still connected to the room is kicked back to the server lobby.
- `configure { options }` (host only)
- `addBot` / `removeBot { playerId }` / `configureBot { playerId, options }` — seat a bot, drop one, or toggle a bot's convention options (`alarmDiscards`, `forcedPlaySignals`, `zeroHintPlaysChop`); all require a seat and the lobby phase. Unknown/non-boolean option keys are ignored.
- `start { seed? }` (host only; works in lobby OR when a finished game is on screen)
- `action { action: { type: 'play'|'discard'|'hint'|'annotate', ... }, reasoning? }` — `reasoning` is optional free text explaining the move, recorded in the save file (see Saved games above); bots send theirs automatically.
- `undo` — roll back the most recent play/discard/hint; only the player who took it can undo it. The undone action's log entries are kept, flagged `undone: true` (clients strike them out with an [UNDO] badge); saves record undo as a distinct event and replay reproduces the struck entries.
- `requestUndo` — toggle a request that the current undo owner (top of the undo stack) undoes. Transient (never saved); cleared by any action, undo, or new game. The owner's view gets `undoRequests: [names]`; others get `canRequestUndo`/`undoRequestedByMe`.
- `abandon` — cast a vote to abandon the current game; on the second distinct vote the game is marked finished with `endReason: 'abandoned'` (same game-over screen as a natural end, so players can review or export the deck order before starting a new one). Voting twice toggles your own vote.
- `react { emoji }` — send an ephemeral reaction (allowed set: 👏 🤔 ❓ 😱 ❗). The server validates, throttles (500ms per connection, silent drop), and relays `reaction { playerIndex, emoji }` to everyone in the room — reactions are never part of game state and never appear in saves. Clients float the emoji over that player's row for 2s (`.reaction-bubble`, re-attached across re-renders). Requires a game on screen (playing or finished) and a seat — spectators don't get a reaction bar. Resident bots emit reactions too (the guard reminder, below): they hold no connection, so `index.js` hands `bots.js` a `sendReaction(roomId, playerIndex, emoji)` hook alongside the broadcast hook in `initBots`, and the same relay serves both paths.
- `exportDeck { file? }` — any player may request the deck order of the finished game; the server replies with `deckExport { data, filename }` for the client to save as a file. Rejected if the game isn't finished (would otherwise leak the remaining draw pile). With `file` it exports a **saved** game instead of the caller's room, which is how the export button on a replay's game-over banner works — a replaying connection holds no seat (it isn't in a room at all), so the seat-scoped path can never serve it. Same rule either way: `deckExportFromSave` reconstructs the save and returns nothing unless it ends `finished`, so an in-progress game (including one continued past its `end` line by an undo) keeps its draw order hidden. Both paths build the payload with `deckExportPayload`, so the two produce identical files.

There is intentionally **no reset action**. To start over before a natural end, two players have to independently click "Abandon game" — that makes a single accidental click harmless. The host can also paste an old seed into the lobby's seed input to re-deal the same deck.

## Player stats

Every log entry carries `at` (wall-clock ms, stamped by `pushLog`; replay overwrites it with the save event's `t` so a reconstructed game reports the times it was really played at). From that, `stats.js` derives per seat: cards played, cards discarded, hints given, hints received, undos, and move time — a move's time is the gap from the previous move (the first counts from `startedAt`), so per-player times partition the game.

- **Undone actions** count as an undo for whoever took it (only that player can undo) and are excluded from the play/discard/hint counts, but their time still counts — the player spent it. Ordering is by `at`, not log order: undo re-appends the struck entries at the end of the log.
- **`MAX_MOVE_MS` (5 min)** caps a single move's contribution. Games get left open overnight; without the cap one AFK gap dwarfs an entire evening of real play and the time column says nothing. The game's wall-clock `durationMs` is reported separately and is *not* capped, so move times can sum to less than the game length.
- **Time share.** Each seat's `timeShare` is its cut of *that game's* move time (the per-game table's "% of game time"). The all-time column is `timeShareAvg`, the plain **mean of those per-game shares** — every game weighs the same, so a single long game can't speak for a player's whole history, and nobody is measured against people they never sat with. Summed time ÷ summed time would do exactly that, which is why the aggregate deliberately doesn't add up like the count columns do. A game with no recorded move time (e.g. abandoned before anyone moved) sits the average out rather than counting as 0%.
- **Seconds per move** (`moveMs / moves`) is shown next to the time. Unlike the share column it is *pooled* across games in the aggregate — it's an absolute pace, so every move counts once no matter which game it came from.
- The finished-game view carries `stats` (null while playing) and the client shows the table on the game-over banner. The lobby's "Player stats" section aggregates across saves by player *name* — the only identity that survives across games, since playerIds are per-room. A name is shown as a bot only if every game it appears in was a bot seat (`botFlags` comes from the room roster or the save header; game state doesn't carry the flag).

## Bot par score

What a table of bots scores when dealt the very same cards — the context a bare score lacks (22/25 means one thing on a deck the bots take 25 from and another on one they only get 20 out of).

- **Computing it** (`botScore.js`): `simulateBotGame` is `benchmark.mjs`'s `playOut` — the same brain, driven through the real rules engine against filtered views, so it can't cheat and an illegal move throws. Pure, and no filesystem, which is what lets `savedGame.js` import it without a cycle. The variant, end rule, player count and `allowEmptyHints` come from the real game (they decide what score is *reachable*); `shareGuarded` is forced on, exactly as the benchmark does, so par is comparable across the library no matter what the humans played with. `botScoreForState` takes the deck off a live state, `botScoreForSaveHeader` off a save header — no need to replay the game itself, since only the deal matters.
- **Storing it**: sidecar `saved-games/bot-scores.json`, keyed by basename, same reasoning as tags — the JSONL stays pure replay data, and a derived number that a brain bump invalidates has no business in it. The entry is `simulateBotGame`'s result (`version`, `score`, `maxScore`, `misplays`, `endReason`, `moves`, `playerCount`) plus `computedAt`. A deck never changes, so an entry only goes stale when `BOT_SCORE_VERSION` (= `BOT_VERSION`) moves; `botScoreFor` recomputes on mismatch, `backfillBotScores` sweeps the whole library. Writes are serialized through one promise chain (the boot sweep and a finishing room can both land on the file). `deleteSave` drops the entry with the tags.
- **When**: `recordBotScore` runs at both game-end paths in `room.js` (natural end and the second abandon vote), caching on `room.botScore` so the view doesn't re-simulate on every broadcast; the server also runs `backfillBotScores` on a background tick after `listen` and re-broadcasts the lobby once when it computed anything. A failure is never fatal — a missing par is simply not shown.
- **Where it shows**: `viewFor` puts it on the finished-game view (`botScore`, null while playing), and the client prints it on the game-over banner next to the final score with the delta vs par; `replaySave` attaches the same field so a replay's banner matches. Library rows show `🤖 score/max`, and the game-info modal shows it with the brain version and how the bots' game ended.
- **The gate**: par is derived from the deck, so it's knowable from move 0 — but it's withheld until the game is finished, for the same reason the seed is. A live game's par is a fact about a deck still in play.

## Seeds and saved games

- Every game has a 32-bit unsigned `seed`. If the host doesn't supply one, the server generates a random seed at game start. The seed is stored on the game state and embedded in the save header under `saved-games/`.
- The seed is NOT exposed in the live view while a game is in progress — it would leak the entire deck. It only appears in the view (and is shown on the game-over banner) once `status === 'finished'`.
- To re-deal an identical starting hand, the host pastes the seed into the lobby's seed input before clicking Start. There is no step-through viewer yet; the save files are the source of truth for reconstruction.

The server broadcasts a fresh `sync` to all connections after every state change. Each client renders from `sync.view` — no client-side game state apart from the latest view.

## Game variants

Defined declaratively in `server/variants.js`. Each variant is a list of *suits*; each suit has:

- `color` — name used in card identifiers and SVG filenames
- `distribution` — array of card values to include (e.g. `[1,1,1,2,2,3,3,4,4,5]` is the standard 10-card suit)
- `direction` — `'up'` (play 1→5) or `'down'` (play 5→1)
- `hintMatches` — `'self'` (only own color hint applies), `'all'` (any color hint matches, like rainbow), `'none'` (no color hint ever matches, like black)

The five supported variants:

| id                              | suits                                                            | deck size |
| ------------------------------- | ---------------------------------------------------------------- | --------- |
| `simple`                        | 5 standard colors                                                | 50        |
| `rainbow`                       | + 10-card rainbow (matches all color hints)                      | 60        |
| `rainbowCritical`               | + 5-card rainbow (one of each number — every card is critical)   | 55        |
| `rainbowCriticalBlack`          | + 10-card black (no color hint matches)                          | 65        |
| `rainbowCriticalBlackReverse`   | + 10-card black played 5→1 with reversed distribution            | 65        |

When adding a new variant, add it to `VARIANTS` and add a row to the deck-size test in `server/game.test.js`. Test invariants (deck size, suit composition) — they catch typos in the distribution arrays.

## Bot player

**Lobby bots (the normal way):** any seated player can add or remove bots from the room lobby via the `addBot` / `removeBot { playerId }` messages (the client shows a "+ Add bot" button and a Remove button per bot). These bots live inside the server process (`server/bots.js`): a bot is an ordinary seat whose turns are driven by `botBrain.decide` against `viewFor(room, botId)` after a human-feeling delay (`HANABI_BOT_DELAY_MS`, default 1200). Each bot carries per-bot convention options (`player.botOptions`, all on by default: `alarmDiscards`, `forcedPlaySignals`, `zeroHintPlaysChop` — the toggleable subset in `BOT_OPTION_KEYS`), edited in the lobby via `configureBot { playerId, options }` (host/any seated player, lobby phase only) behind a ⚙️ panel next to each bot. The driver builds the bot's `conventions` from those options (`conventionsFromOptions`, merged over the standard set) and passes it to both `alarmGuards` and `decide`, so each convention governs both using and reacting to the signal. Options ride in the lobby view (`botOptions` per bot player) and default back on for resumed bots. At most `MAX_TOTAL_BOTS = 10` bots across all rooms; the lobby view carries `botSlotsFree`. Bots can only be added/removed in the lobby phase; they are tagged `isBot` in every view, don't keep a room from being idle-deletable (`isRoomIdle` ignores them), are freed when their room is deleted or closed, and are skipped when host transfers on leave. **Guard reminder (human partners):** an alarm discard is only half a signal — it works because the next player answers it by guarding their oldest unclued card(s), which is what moves their chop off the danger. A human can simply forget to click, and the forgotten mark is invisible as a mistake: the bot reads the shared guard flags, sees none, and plays on believing the criticals are still exposed while the human believes they were warned. So after raising an alarm the bot records what it asked for (`noteAlarm`: `alarmGuardTargets` — the receiver's oldest 1–2 unclued, unguarded cards, the same helper `alarmGuards` and `recordInferredGuards` use), and on its next turn, if the receiver guarded nothing new, it says so before moving (`remindGuards`): two ❗ reactions `HANABI_BOT_REMIND_GAP_MS` (2000) apart, then it holds its turn open for `HANABI_BOT_REMIND_WAIT_MS` (12000) so the marks can appear. Annotate is turn-free, so the guard lands mid-wait and the resulting broadcast pokes the bot, which stops waiting and plays at once (`pending: 'remind'`). Deliberately narrow: **only when `shareGuarded` is on** (with guards private the bot can't see the answer at all and infers it instead — `inferredGuards`), never toward a bot seat (it guards on its own) or an offline one (nobody to remind, and the table would stall), and **once per turn** — an unanswered nag is dropped rather than repeated every turn that follows. *Any* newly guarded card counts as an answer, not just the named ones: a human may reasonably mark a different card, and the slip being caught is forgetting entirely. **Undo interacts with it three ways**, all following from "a nag belongs to the turn it was raised on": a human undo that rolls that turn away cancels the chain at the next poke but leaves the alarm *armed* — the warned-about move is being replayed, so the warning is owed again (spending it there let the replayed turn go unwarned, the exact mistake the reminder exists to catch); the bot's own `botUndo` clears it outright, since the alarm being unmade is the move it asked about; and an undo request **preempts a nag in flight** the same way it preempts a queued action — asking about guards is moot on a turn about to be rolled back, and holding the request for the nag's ~14s then stranded it entirely (`botAct`'s stale-schedule return left nothing to re-poke). It keys off the decision's *reason*, not the kind of card thrown, so it covers every alarm type — including the free trash alarm, which needs it most: on the table that one looks like the most routine move in the game, so it is the easiest of them all to sit through. The reminder also lapses if the pointed-at cards leave the hand (too late) or get clued by someone else (off the chop anyway).

If a bot's action tops the undo stack, a `requestUndo` makes the bot undo it, then pause (`HANABI_BOT_UNDO_GRACE_MS`, default 6000) so the requester can chain their own undo. Repeating that pair walks back as many moves as you like: a bot holds at most one scheduled task (`pending: 'act' | 'undo'`), and a fresh undo request **cancels a queued action** rather than queueing behind it — the queued move is the replacement the bot lined up when the previous undo put it back on turn, and letting it hold the slot left the next request unscheduled forever (it fired later, found the turn rolled away, and returned as a stale schedule with nothing left to poke). The bot registry is keyed by **room id + player id**, never player id alone: a playerId is unique within a room but resume/branch reuse the ids in a save's header, so one save opened as two rooms (a resume plus a branch of it) gives both rooms a bot seat with the same id — under a playerId-only key the second room's seat looked already-staffed and the entry's `roomId` still pointed at the first room, so `notify` announced its moves to the wrong room and its own players watched the bot sit frozen. Bot seats in a resumed or branched save are re-staffed by `adoptRoomBots` (the `isBot` flag in the save header, falling back to the built-in bot names), so they play on without being re-added; seats past the global cap stay offline for a human to claim.

**CLI bot:** `node bot.mjs` (or `npm run bot --`) runs the same brain as a normal WebSocket client, e.g. from another machine. Decision logic lives in `server/botBrain.js` as a pure function `decide(view, conventions)` — it sees only the same filtered view a human gets, so it cannot cheat by construction. Transport, reconnect, and CLI flags live in `bot.mjs`.

Conventions (the `standard` set in `CONVENTION_SETS`, selectable via `--conventions`): oldest card is leftmost; a colour hint marks for play the *newest touched card the receiver cannot already prove unplayable* — the target **slides** past provably-dead touches (with empty piles and a hand of `[green 5, green 1, red 2, green 2, black 5]` whose two 2s are number-clued, a "green" hint touches slots 0/1/3 but targets **slot 1**, because slot 3 is a known green 2). Tracked via `lastHints` markers, which the server consumes when any card of that hint leaves the hand; **every** colour hint still marked on the hand stays a pending play target (played oldest-hint-first). The receiver **trusts** the hint: the sender chose the target and can see the card, so a merely *possibly* playable target is played. There is deliberately **no last-fuse "prove it" tightening** — requiring `knownPlayable` at `fuseTokens === 1` stranded the card forever while the sender, counting it as a pending play, withheld all further help, deadlocking both sides into stall-hint loops. `hasPendingPlay` uses the receiver's exact reading (`colorPlayTargets` takes the same `possible(slot)` predicate, and the giver's `playHintCandidates` mirrors it), so sender and receiver can never disagree about what will be played. If a colour hint fully pins another touched card AND that card is playable, the pinned card is played first (its play consumes the hint's markers, retiring the target); a pinned-but-unplayable card is simply skipped by the slide (do NOT cancel on any pin: colour hints unavoidably touch rainbow cards, so that reading makes all colour hints self-cancel once a rainbow card is known). Because those markers are consumed when *any* card of the hint leaves the hand, a colour target's play obligation would be lost if the receiver discards an older card that merely shared the hint (a forced or alarm-convention discard) before playing the target; to survive that, the bot records each live colour target's card id in the driver memory and rescues it across such a discard — but not across a *play* (a pinned-playable sibling played first deliberately retires the target), keyed on whether the bot's own last hand-exit was a discard or a play (`rememberColorTargets`/`mergedColorTargets`/`myLastHandExit`; without memory this degrades to marker-only, so rollouts and the CLI bot are unchanged). A number hint means *keep* unless a card becomes provably playable, except a **"1" hint**, which asks for every touched card to be played (oldest first) while it can still be a playable 1 — unless a touched 1 is pinned to a single identity (then it's information, e.g. "that's the dead duplicate"). **The "1" exception is itself void for a card that could be a reversed suit's own 1** (`onesPlayObligations`): where a suit plays 5→1 its 1 is the pile's *last* card and, with the reversed distribution, its only copy — a critical card, the opposite of a play cue — so in such a variant a "1" hint plainly means *keep* until the receiver can rule that suit out. Being touched by any colour hint rules it out (a `hintMatches: 'none'` suit like black is never in a colour hint's touched set), as does copy-counting the single black 1 elsewhere. Variants with no down suit are unaffected. **What the order comes to is read in exactly one place** (`onesPlayOrder`: the obligation, the pin exception and the last-fuse gate together), by the receiver playing them, the giver's `hasPendingPlay`, the dead-1 warning and — the case that forced it — the *saver*. `findSaveHint` used to screen the "1" keep-hint with a bare `possiblyPlayable` ("they'd misfire on it"), so in a reverse variant it refused to give the one hint that can protect a black 1 on the chop: black is never in a colour hint's touched set and the card isn't playable, so the number hint is the only save there is, and the receiver's own rule reads it as a keep. The variant's most critical card was the one card the bot could never save; it discarded and let it go. On the last fuse the "1" hint is trusted only while the order is **fresh** — no 1 played by *anyone* since the hint (`onesOrderIsFresh`/`onesPlayGate`, shared by receiver, giver model and dead-1 warning). The hinter verified every obligated 1 was playable when giving the order, so it can only have died if a 1 has been played since and taken its colour, which the receiver can't see. A fresh order is trusted for its **oldest** 1 only; anything else demands `knownPlayable`. Counting the receiver's own 1-plays too is deliberate — only the order's 1s are guaranteed distinct colours, and it caps the trust at the first 1 of an order. (Trusting the whole set unconditionally, ignoring staleness, was measured and is much worse: −0.05/row with fuse-outs up.) **A "1" is therefore never a valid stall value** while `playAllOnes` is on — `findStallHint` skips it, since a "1" hint is a play order, not filler; stalling with one used to hand the receiver a fatal misfire. **Dead-1 warning** (`findDeadOneWarning`, sender-side): the receiver can never detect that an obligated 1 has *died* — it knows the card is a 1, not its colour, so while any colour's 1 is open the card stays possibly playable and its own dead-card gate can't fire. Only a player who can see the card knows, so when the next 1 a teammate would play is already on the pile, the bot hints that colour: it pins the card to colour + the known 1, making it provably unplayable (their gate now fires) and, via the reveal exception, turning the "1" order back into information. Candidates that would leave a misfiring colour target behind are rejected. Value scales with the fuses, so it is offered above even a save at 1 fuse, above ordinary play hints at 2, and only as a last resort at 3. **Zero-card-hint convention** (`zeroHintPlaysChop`, only when the room enables empty hints): a hint touching *none* of the receiver's cards means "play your chop". The receiver honours it above everything, even a save (its own next action would consume the signal, so deferring loses the command); the sender uses it as a fallback when a player's chop is playable but no ordinary play hint reaches it (a colour would point elsewhere, a number is ambiguous), picking a colour/number the receiver wholly lacks (`emptyHintChopSignal` receiver-side, `findEmptyHint` sender-side). **Yield** (`yieldDuplicatePlays`, `yieldSlots`): when a convention marks one of our cards for play *and* pins what it must be — exactly one of its remaining candidate identities is playable, so a blue target on an empty blue pile can only be the blue 1 — and a teammate is already obliged to play that same identity, the copy is ours to shed, not to race for; we discard it and they play theirs. The implied identity is read only off slots a convention actually marked (applied to any card it is nonsense: an unrelated red card on an empty pile would "imply" red 1). We yield only to a teammate who *cannot* pin the identity themselves (a "1" hint gives them the number, never the colour) — otherwise both sides yield and both copies are discarded. A yield is externally identical to a touched-discard alarm, so `alarmGuards` disambiguates from the only vantage point that can: a yield happens only for a card the *reader* is obliged to play, so when the discarded identity is one our own obligation could satisfy, it reads as stepping aside, not as a warning. Discard priority is provably-useless card → yielded duplicate → chop (oldest untouched) → forced (the **least dangerous** card by `discardRisk`, ties to the oldest, and **skipping our own guarded cards** while anything else is throwable — guarding was our answer to an alarm, the strongest statement the conventions have that a card must not go, and `discardRisk` cannot see it: a wholly unclued guarded card reads as the safest thing in the hand precisely because nothing is known about it) — but when every card is clued and even that pick could still be critical, the bot stalls with a harmless hint instead while tokens remain. `discardRisk` is the conditional expected pile-point loss of throwing one of our own cards: each candidate identity's `discardCost` weighted by how many copies of it are still unseen. It replaced an all-or-nothing `provablyCritical` screen that took the *oldest* card not provably a last copy — a card reading `{red 1, red 2, red 5}` with the red pile on 4 passes that screen (two candidates are already played, so not last copies) and got thrown ahead of a card known to be a spare, losing the red 5. **Free gamble** (`gambleChance`): a card whose every candidate identity is either already played or playable *right now* is worth nothing kept — the dead candidates never become playable, so it will never be worth more than this turn. Playing it risks no pile points (it scores or burns a fuse) while discarding it forfeits the point, so when the forced pick is risky (`discardRisk > 0`), the odds are better than even and a fuse can be spared, the bot plays it instead — ahead of the stall too, since a stall defers the same choice to a turn when the piles haven't moved. Deliberately *not* ranked ahead of an ordinary safe discard: measured, that scores no better and quintuples fuse-outs, because while something safe can be thrown the card can simply wait and its odds only improve as the piles grow.

**Choosing among several plays** (`playUnlockScore`): when the conventions oblige more than one play, all of them get played sooner or later, so the choice is one of *order* — and the teammate decides it. Candidates are ranked by how many of their cards the play turns into a play **they can see** (`knownPlayable` from their own deduction; a card they cannot tell is playable is not yet a play to them), averaged over the identities our own card might be, weighing only its playable ones. Their deduction isn't re-run against the new pile, so it under-counts rather than over-promises. **Only ever a choice within a certainty class** — provable plays, then colour targets oldest-hint-first, then 1s — because a provable play jumped by a merely-trusted one trades information for tempo and loses: the certain card lands first, and what it puts on the pile can prove the trusted one dead before we ever risk it (measured: ranking across classes moved fuse-outs 20 → 27 per 3000 games for no score).

Own-card deduction combines hint constraints with *copy-counting* (an identity whose every copy is visible — played, discarded, or in a hand the deducer can see — is ruled out) plus *cross-card elimination* (a card pinned to a single identity claims a copy, iterated to a fixpoint). The same deduction, restricted to what the receiver can see, drives hint-giving: all valid play hints are enumerated and scored (plays caused, how soon touched cards matter, information, minus useless/duplicate touches; colour hints outrank number hints as a class — except a number hint that starts *strictly more* cards playing wins, so a single "1" hint that sends two 1s beats a colour hint revealing one). Saves: a critical or lone-2 chop is saved (**the lone-2 save is a precaution, not a rescue** — the twin is still out there, so it gets none of a last copy's latitude: `loneTwoWorthSaving` requires **3 tokens** rather than 2, refuses a **suit played 5→1** where the 2 is the second-to-last card of its pile rather than an early one, and is dropped when the hint we settle on would **lock the receiver** out of discarding (`hintWouldLock`) — locked, they can only stall or throw a card the team paid a hint to keep, which is worse than one 2 down. A certain last copy is still saved at any token count, in any suit, locked hand or not) — by a play hint when the card is playable now, by a pinning colour hint when that proves it unplayable, else by the number keep-hint — for the next player, or for a later player when everyone in between has a pending play. Saves look one move ahead: a keep-hint slides the receiver's discard onto their next unclued, *unguarded* card (a guarded card is off the chop, so the slide skips it — otherwise the bot mistakes an already-guarded critical for a second endangered card and re-alarms), and when that card is save-worthy too, the bot saves whichever loss costs more pile points (losing an early critical truncates its whole pile). The pile cost is the true `discardCost`, so a lone-2 whose twin is still in the deck (save-worthy but not `identityCritical`) weighs 0 there — it must not outrank a certain last-copy or provoke a self-sacrificing alarm to protect it. **2-player play-hint deferral**: when the next player's chop is save-worthy but not playable now (so the save would only park it behind a clue) and that player also holds a hintable play, the bot gives the play hint instead of the save — a hinted player plays rather than discards, so the chop survives untouched, and because 2-player turns strictly alternate the bot re-saves it next turn (buying tempo, and sometimes a token when a same-colour draw later lets one hint cover both). Restricted to 2-player and skipped in the final round; a play-save (chop playable now) still wins outright. At full tokens it stalls with a harmless number hint. **Protective stall** (`protectiveStall`): whenever the bot is forced to stall — no play and nothing safe to discard, but tokens remain — it spends that otherwise-wasted token protecting a partner's save-worthy chop if one exists, even when the partner has a pending play (so the primary save above was skipped on the assumption they'll play). It's free insurance against a partner who dumps their critical chop anyway (a human misread, or a differing view); it costs nothing when they do play. Falls back to the harmless keep-hint when no chop needs protecting. **Sweep save** (`findSweepSave`): in rainbow-bearing variants one colour hint touches every rainbow card, so it can clue two rainbow criticals at once with the hint's newest touched card being provably dead (a harmless forced misfire, or the receiver just keeps it) — it risks *no* pile points and costs at most one fuse, so it's preferred over a discard alarm whenever it exists and a fuse can be spared (`fuseTokens ≥ 2`). **Alarm convention**: when hints can't cover the danger (no tokens, or one hint can't protect two endangered cards whose loss is expensive) and no sweep applies, the bot makes an out-of-the-ordinary discard — provable trash while holding an obvious play, a useful touched card, the chop despite an obvious play, a card past the chop, or a cheaper critical, in that order of safety — and the next player reacts by guarding their oldest unclued card(s) with the annotate interface. The first of those is the **free alarm**: a card proved worthless costs no pile points and no fuse to throw, so the forgone play is the entire price *and* the entire signal, which is why it outranks burning a useful card or gambling the unknown chop. It needs that play — without one, throwing trash is the most ordinary move in the game — and prefers an *untouched* trash card, which no partner can misread as a yield (that reading only ever applies to a touched discard). "An obvious play" means any play the conventions oblige, not just a provable one — **a colour hint is an obligation to play**, so declining one to discard the chop is exactly as loud as declining a known-playable card (a colour target is only ever *possibly* playable, so an earlier `knownPlayable`-only test missed the case the convention most wants to catch). **Declining an obliged play makes *any* discard an alarm, not only a chop discard**: the receiver checks it before the touched-discard screens, which would otherwise write the discard off as routine (the thrown card was provably dead) or forced (every card clued, so there was no chop to throw). Neither reading holds when a play was there to be made — throwing known trash costs the discarder nothing *but* the forgone play, which makes it the cheapest alarm available rather than the quietest move available, and a chopless hand has no other way to raise one. **An alarm has to be a choice we made**: either a play declined, or a chop we could have thrown instead. With neither — no chop, no play — every option was a bad discard and throwing the cheapest is damage control, which is exactly how the far end reads it (`alarmGuards`' `senderFree` screen), so `findAlarmMove` raising one there was the two sides drifting: it asked for guards nobody could hear it ask for. Emission and detection are otherwise **the same `hasPendingPlay` call** (`findAlarmMove` sender-side, `alarmGuards` receiver-side), so the two ends cannot drift on what counts as a forgone play — and the sender asks it **from the receiver's chair** (`hasPendingPlay`'s `reader` argument deduces our hand without counting the reader's cards, since they cannot see them): a play provable only from cards in *their* hand is, to them, no reason for anything, so declining it signals nothing. The drift is one-directional — their deduction is strictly weaker — so matching it closes it. Two more of the same kind: the receiver asks whether the thrown card was dead **when thrown**, not now (`deadWhenThrown` — the pile cap it reads already counts the discard, and sacrificing the last copy of a needed card is exactly what caps its pile short of it, so every deliberate sacrifice used to read as trash); and the sender *prefers* a provably-useful touched card over a merely-possibly-useful one, which lands dead often enough to be dismissed — a preference, not a rule, because requiring it cost 49 perfect games per 3000 and the alternative to a shaky signal is silence over a certain danger. it reads live `lastHints` markers only, never the sender's private memory, which is precisely what the partner can reconstruct. The alarm is cheap for the sender because the chop is untouched: throwing it consumes no hint markers, so the colour target survives in hand (memory keeps it across a discard) and is played the following turn (2 cards when the alarmer still had tokens, 1 when they had none), which moves their chop (`alarmGuards` receiver-side, `findAlarmMove` sender-side; drivers apply guards before deciding since annotate is turn-free). The risky discard types (burning an unknown own card) are gated by expected value: a static ≥2-point endangered-value threshold mid-game, relaxed in the late game (deck ≤ 10) to a direct test — sacrifice only when the certain save exceeds the specific card's `expectedDiscardCost` (an unclued card near the end is mostly spent copies, ~0.5 on average), because near the end the alarm's downstream cost of clogging the partner's hand with guards nearly vanishes. Guard flags feed back into the sender's chop model when the room shares them (`shareGuarded`; the benchmark and bot-vs-bot tests turn it on). When guards are *not* shared the sender can't see them, so it remembers what its own alarms prompt — the receiver guards their oldest 1–2 unclued cards — in driver memory (`inferredGuards`) and re-applies them each turn (`recordInferredGuards`/`applyInferredGuards`), so it doesn't re-alarm cards it already got guarded. Once the deck is empty and ≤6 cards remain in hands, an **endgame search** enumerates the consistent identities of the bot's own hand and simulates every legal action to the game's end with the real rules engine, taking the best worst-case outcome (fuse losses penalised). Because it models the partner as this same bot, once a win is guaranteed every move scores equally, so a **human-partner tie-break** (`endgameHelpfulness`) orders genuine (worst, avg) ties: a hint that hands the partner an actionable play ranks above a discard or a real gamble, above a hint touching only dead cards (inert to a bot, but a human may read it as a play cue and misfire), above "playing" a provably dead card (a guaranteed wasteful misfire, strictly worse than discarding it). This never lowers the worst-case score — it only picks the least reckless, most legible move among equally winning ones. **Forced-play signals** (2-player, token-starved deadlock, needs the driver-owned memory object passed as `decide`'s third argument): when one player is fully locked and the other holds a play fully determined by shared knowledge, the free player's discards advance a pointer over the locked player's possibly-playable cards (oldest first) and their eventual play commands the pointed card played; while armed, the free player's plays are only made as signals (`forcedPlayStep`). "Fully locked" means no `hasPendingPlay`, not merely no *provable* play — a colour-clued seat is obliged to play and was never stuck, and treating it as deadlocked pointed the order at some other card. The **free seat must have a chop too**: a play only *means* anything if its maker could have discarded instead, so with every card clued or guarded their turn was play-or-throw-a-keeper and carries no order. One test, read from both sides (`deadlocked`) — the free seat as "my play would be taken as a command", the locked seat as "their play was one"; it reads guard marks, so like the rest of the chop model it wants `shareGuarded`. The converse binds us too: **while the partner is locked, our play IS an order, so one we don't mean is not ours to make** (`commandedPlayCost`). We weigh what they'd throw at it against the discard we'd make instead, and stay quiet when the order is dearer. What they'd throw is the card the pointer **actually reaches** — their oldest possibly-playable one, since nobody is counting advances here (a bot that really is signalling answers in `forcedPlayStep` and never reaches this gate); a really-playable one costs nothing. Pricing the *worst* card the pointer could ever reach instead let one expensive card anywhere in a locked hand silence every play, turn after turn. Gated at `hintTokens === 0`: a signal is only ever *sent* at zero tokens, so zero is the only place a play of ours can be taken for one — with a token banked the partner isn't stuck, a hint gets them out of it, and holding back there just made them spend the token stalling while we sat on a card they had hinted us to play. Staying quiet still leaves the better half of the turn — a hint if we have one, and if not, a discard that hands them a token. **Only a discard made while we were already armed advances the pointer**: the turn we first read the deadlock starts the count at 0 and stops there. The sender agrees by construction — it advances only over a hand that already has no chop — and the case that forced this is exact: an alarm discard is answered by guarding our chop, which is itself what locks the hand, so the very discard that armed us was being counted as an advance and the partner's next play commanded one card too far. A guarded card *is* a legal pointer target (a guard says "too dangerous to discard", not "unplayable", and the sender can see what it points at). Note this whole convention is bot-to-bot machinery — a human partner who plays a card simply because they want to play it reads as having sent a command, which is what the per-bot `forcedPlaySignals` option is there to turn off.

`BOT_VERSION` in `botBrain.js` names the current brain; `bot-performance.md` records what each version changed and its full benchmark table. Bump the version and add an entry (run `npm run benchmark` before and after) whenever the decision logic changes.

Flags: `--server URL` (default localhost:3000), `--room ID` or `--create [--room-name X]` (default: join the newest lobby room, else create), `--name`, `--delay MS` (thinking pause, default 900), `--autostart N` (start when N players are seated, only if the bot is host), `--seed S`, `--conventions standard`.

Testing: `server/botBrain.test.js` crafts exact decks (dealing is round-robin: player 0 gets draws 0,2,4,…) to pin each convention, plus bot-vs-bot full games on every variant that must end legally — `rules.js` throws on any illegal action, so a completed game doubles as a legality proof. Typical scores: ~20–22/25 on `simple`, perfect games on good seeds.

## Card art

User-provided card images go in `client/cards/` with the naming convention `{color}-{number}.{ext}` (e.g. `red-3.png`, `rainbow-5.webp`, `black-1.svg`). The client always requests `/cards/{color}-{number}` (no extension); the server probes for `.png`, `.webp`, `.jpg`, `.jpeg`, `.avif`, `.svg`, and `.gif` in that order and serves whichever it finds, so the host can drop any supported format without touching code.

## Deployment

The host runs `npm start` on their machine and shares the URL `http://<their-tailscale-hostname>:3000` with players. Tailscale handles NAT traversal and end-to-end encryption — do not add TLS, auth, or any other access control to the server; that's the tailnet's job. Anyone on the tailnet is trusted.
